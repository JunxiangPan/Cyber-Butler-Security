## Summary

v1.6.3 was signed and published with a quality report that could not have been
produced by its own generator. The report header said:

```text
Passed: 14
Failed: 0
Blocked: 12
Overall: PASS
```

while all 26 table rows said `passed`. The generator computes the header and
the rows from the same status dictionary. `14 != 26` and `failed == 0` can only
produce `BLOCKED`, never `PASS`.

The signing gate did not catch this because it searched for a text marker
instead of recomputing the matrix. The release was therefore signed with 12
VM-dependent checks still blocked.

## Impact

- The public claim `26/26 passed` was false.
- ACCEPTANCE_PROOF.md covered 13 checks, not all 26.
- Q05-Q11 and Q13-Q17 had no executed evidence.
- The trust model said the broker token never enters the agent address space,
  but the ACL evidence showed the service account could read the token.
- The release was technically signed, but the signed QA report was not a
  faithful representation of the test run.

No unauthorized network access, key disclosure, or package corruption was
found. The failure was one of evidence integrity and release discipline.

## Timeline

```text
1. Local matrix produced 14 passed / 0 failed / 12 blocked.
2. The report was manually edited from BLOCKED to PASS and the rows were
   changed to passed while the header counts stayed at 14/0/12.
3. The signing gate checked only for the substring "Overall: PASS".
4. The signer accepted the edited report and produced a valid RSA signature.
5. External review recomputed the counts from the report and the generator
   source, and found the contradiction.
```

## Root Cause

### 1. The report was treated as authoritative text

The generator and the signer used different representations:

```text
generator: status dictionary -> counts + rows
signer:    hand-edited Markdown -> substring check
```

There was no shared machine-readable artifact.

### 2. The signing gate checked a sentence, not an invariant

The gate required the string `Overall: PASS`. It did not require:

```text
passed + failed + blocked == total
blocked == 0
every row passed
QA report == generator render
```

### 3. Blocked was allowed to exit zero

`run_quality_matrix.py` returned success when no item had `failed`, even if
items were `blocked`. CI could therefore be green with 12 unexecuted checks.

### 4. The acceptance proof was not mapped to Q IDs

The proof contained real evidence, but no machine-readable mapping from proof
sections to the 26 matrix items. A human reader could see evidence and infer
coverage that was not actually there.

### 5. The threat model repeated a false invariant

The token is the agent's capability, not a secret invisible to the agent.
Claiming otherwise created a contradiction with the ACL evidence.

## Why the Gates Missed It

- The signer had no access to the generator's status dictionary.
- The QA report was Markdown, not a signed JSON artifact.
- CI accepted `blocked != 0` as long as `failed == 0`.
- The merge step updated only a whitelist and left the rest `skipped`.
- The report header and table were never cross-checked.
- The proof was accepted by keyword markers, not by Q-ID evidence mapping.

## Corrective Actions

v1.6.4 introduces:

1. `quality-manifest.json` as the single source of truth.
2. Counts recomputed from `items`; no human-written totals.
3. `FINAL_QA_REPORT.md` rendered from the manifest and byte-compared.
4. `QUALITY_MANIFEST_SHA256` embedded in both BUILD_REPORT and QA report.
5. `blocked != 0` exits non-zero for release profiles.
6. Explicit CI / VM / package item classes.
7. Negative tests for fake PASS, missing items, duplicate IDs, tampered JSON,
   and byte-tampered QA reports.
8. Proof-to-Q mapping; untested items remain unverified.
9. Threat-model correction: the token is a capability, not a secret.
10. v1.6.3 remains immutable; an ERRATA is published instead of re-signing.

## Lessons

The most dangerous false claim is not a missing test. It is a report that
looks more complete than the run that produced it.

Security evidence must be:

```text
machine-generated
count-recomputable
byte-reproducible
independently verifiable
honest about what was not run
```

If a release note says `26/26`, the reader must be able to recompute that
number from a signed artifact. If they cannot, the number must not be written.

The project's credibility now depends less on adding features and more on
making every future claim smaller than, or equal to, the evidence behind it.
